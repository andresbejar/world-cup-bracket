## Problem Statement

A web app where the user's friends and family compete to predict the results of the FIFA 2026 World Cup. Each user predicts match scores and outcomes across all 104 games, plus the tournament's top-3 finishers. Points accumulate. The user with the most points by the Final wins a prize.

Built for fun, not for venture-scale users. Target audience: ~5–50 family members and friends. Hard deadline: opening match on **June 11, 2026** (~30 days from today, 2026-05-09).

## What Makes This Cool

- **Predict the entire bracket on day 1, refine as you learn.** Users build their full prediction (group stage through Final) up front. As actual results come in, they can keep editing future-round predictions until 4 hours before each round starts. Feels like setting up a chess plan and adapting under fire.
- **Side-by-side reality check.** Once real games finish, the bracket UI shows predicted result next to actual result, color-coded green for hits and red for misses. The user always sees what they had locked in versus what the world delivered. This is the heart of why brackets are fun.
- **Single global leaderboard.** Everyone in the app competes on one ranked list — bragging rights are real. Simple, no league management.
- **No frills.** No trash talk, no risk multipliers, no live commentary. Just nail the basics. The World Cup itself supplies all the drama.

## Constraints

- **Hard deadline: 2026-06-11.** ~30 days. No slipping. If a feature can't ship by opening night, defer it or cut it.
- **Hobby effort.** Solo developer, evenings and weekends. Realistic budget: 3 weekends of focused work.
- **Free-tier only.** Vercel free + Supabase free + api-football free tier. Total cost target: $0/month + domain (~$12/yr).
- **~5–50 users.** No need to design for scale beyond that.
- **Solo operator.** No on-call rotation. App must mostly run itself once shipped.

## Premises (agreed in office hours)

1. **FIFA has no public API.** Match data comes from **api-sports.io direct (Pro plan, host `https://v3.football.api-sports.io`, header `x-apisports-key`)** — NOT the RapidAPI proxy. Rate limit is **7,500 req/day** (verified APT-1, 2026-05-09), so hourly polling uses ~0.3% of the budget. Static fixture/team data (groups, schedule, R32-onwards bracket structure) is **hand-curated and seeded** from FIFA's published 2026 bracket — api-sports is a results feed, not a source of truth for fixtures. Confirmed: the API only returns the 72 group-stage fixtures for league=1 season=2026; knockouts populate post-group-stage. **Subscription end date 2026-06-10 — verify auto-renew before opening night.**
2. **Users predict the entire bracket on day 1.** Predictions cascade through FIFA's published bracket structure. Each round stays editable until 4 hours before that round's first match. Once a round starts, it locks.
3. **Score:outcome point ratio is 3:1.** This rewards luck heavily (real soccer scores are noisy), but for a friends-and-family pool that adds drama, not subtracts from skill. Intentional.
4. **The app is publicly accessible.** Google SSO is open to anyone. If the URL escapes the family chat, strangers can join the global leaderboard. Acceptable for a hobby.
5. **Scoring is recomputed when match status flips to "finished."** Triggered by the polling job, not live during play. Plenty fast for a family pool.
6. **30-day timeline is non-negotiable.** Opening night is opening night.
7. **Knockout-round canonical score = 90 min + extra time, before penalties.** Use api-sports's top-level `goals.home` / `goals.away` fields — these already represent the regulation+ET total (verified APT-1: Argentina vs Ecuador 2024 returned `goals = 1-1`, `score.penalty = 4-2`, `status = PEN`). Ignore `score.penalty`. Score predictions must match this; outcome predictions for knockouts must pick a winning team (no ties), since penalties decide ties IRL.
8. **All write paths are server-validated.** Predictions can only be saved/updated by Next.js API routes that re-check the round's lock state server-side. Supabase Row-Level Security blocks direct client writes to `predictions` after lock. Trusting the client is a no.

## Approaches Considered

### Approach A: Next.js + Supabase + api-football  *(CHOSEN)*

Standard modern stack. Next.js App Router on Vercel for frontend and API routes. Supabase for Postgres, Google SSO, and realtime subscriptions. api-football free tier polled hourly via Vercel cron for fixtures and results. Scoring runs server-side after each match's status flips to "finished." Manual fallback: edit the database via Supabase studio if the API misbehaves.

- **Effort:** M (~3 weekends)
- **Risk:** Medium. api-football data quality for the 2026 World Cup is unverified — must test early.
- **Cost:** $0/month at family scale.

### Approach B: YOLO MVP, manual data entry

Same Next.js + Supabase, but skip the sports API. Hard-code the 104-match fixture list as a JSON seed. Build a tiny `/admin` page where the user enters scores manually after each match.

- **Effort:** S (~1.5 weekends)
- **Risk:** Low technical, high operator burden — the user becomes the SLA.
- **Rejected:** the operator burden over a month-long tournament will sour the project by week 2.

### Approach C: Hybrid — API + admin override

Approach A plus a real `/admin` override page so any match score can be manually corrected if the API is wrong, late, or missing.

- **Effort:** M-L (~3.5 weekends)
- **Risk:** Lowest, most resilient.
- **Rejected for MVP:** the override page is real work for a scenario that may never trigger. Can be added later if the API disappoints. Approach A's "edit via Supabase studio" escape hatch is sufficient for v1.

```
                -- stage: 'group' | 'r32' | 'r16' | 'qf' | 'sf' | 'third_place' | 'final'
                -- matchday: 1|2|3 for group stage rounds (each matchday is its own round
                --           with its own deadline); null for knockout rounds

bracket_slots (id, round_id, slot_label, real_team_id)
                -- slot_label: e.g. "winner-group-A", "runner-up-group-C", "best-3rd-slot-1"
                -- real_team_id: NULL until the upstream stage finishes; populated from
                --                api-football results (or hand-corrected via Supabase studio)

matches       (id, round_id, home_slot_id, away_slot_id, scheduled_at,
               home_score, away_score, status, source)
                -- home_slot_id/away_slot_id reference bracket_slots — knockout matches
                -- exist as concrete rows from day 1, with team identities deferred
                -- group-stage matches have slot_labels like "team-arg" / "team-mex"
                -- with real_team_id pre-filled (since group teams are known up-front)
                -- source: 'api' | 'manual'
                -- status: 'scheduled' | 'in_progress' | 'finished'

predictions   (id, user_id, match_id, predicted_home_score, predicted_away_score,
               predicted_winning_slot_id, points_awarded, created_at, updated_at)
                -- predicted_winning_slot_id: only used for knockout-round outcome picks;
                -- for group stage matches, the outcome is derived from the predicted
                -- score (home_score > away_score → home wins, etc.)
                -- (predictions.locked_at removed — lock state is computed from
                --  rounds.locked_at, no need to denormalize)

finalist_picks (user_id PK, first_place_team_id, second_place_team_id,
                third_place_team_id, points_awarded, locked_at)
                -- INDEPENDENT side bet from the bracket cascade. Locked at tournament
                -- start (deadline = first match kickoff). User can predict "Argentina
                -- wins it all" here even if their bracket cascade has Brazil winning
                -- the Final. Both bets pay out independently.

predicted_third_place_assignments (user_id, slot_id, predicted_team_id)
                -- ONLY for the 8 R32 slots that take third-place teams. User picks
                -- one of their 12 predicted third-place teams per slot, via dropdown.
                -- Every other slot (group winners + runners-up + downstream knockout
                -- slots) is COMPUTED on read from group standings + predictions.
                -- Single source of truth: predictions + group standings. No drift bug.
```

### Group Standings Algorithm (FIFA order)

For computing user-predicted group standings (and for sanity-checking real standings):

1. Total points (3 win / 1 draw / 0 loss)
2. Goal difference
3. Goals scored
4. Head-to-head points among tied teams
5. Head-to-head goal difference among tied teams
6. (Real tournament adds disciplinary record + drawing of lots — we **stop at step 5** for predicted standings since neither is predictable. If predicted standings still tie at step 5, fall back to alphabetical team code as a deterministic tiebreaker — flagged in UI so users know they should adjust their predictions to break the tie.)

### Bracket Cascade Logic

**Prediction phase (before June 11):**
- User predicts group-stage match scores (3 matchdays per group, scored independently).
- App computes group standings from predictions using the FIFA order above.
- For the 24 group-winner / group-runner-up R32 slots: deterministically populate using FIFA's published 2026 bracket structure (encoded as a static JSON map — `winner-group-A` → R32 Match 1 home, `runner-up-group-C` → R32 Match 1 away, etc.).
- For the 8 R32 slots that take third-place teams: present each slot as a **dropdown** of the 12 third-place teams from the user's predicted standings. User picks one team per slot. Each slot displays a **`+1 pt if correct`** affordance — these picks are an explicit side-bet (see Scoring section), not just data entry. Same team cannot be picked for two slots; UI prevents duplicates. Avoids encoding FIFA's ~495-permutation tiebreaker lookup table while turning what would have been a tedious mechanic into 8 stakes-bearing predictions.

#### UI Notes — Third-Place Slot Picks

- **Affordance treatment:** the `+1 pt` label sits in the same visual family as the deadline countdown text (small monospace, ~11px, neutral grey). Visible but quiet. If it screams, it reads like a leaderboard mechanic instead of a quiet bonus, and casual family members will feel pressured by 8 stakes they didn't ask for. Keep it whisper-loud.
- **Placement:** to the right of each slot dropdown, on the same row. Not above, not below — same line keeps the visual rhythm of "8 paired pickers" intact. Pre-finalize state.
- **State after group stage finishes:** once FIFA places real third-place teams in the 8 slots, swap the `+1 pt` label for the result coloring used elsewhere in the predicted-vs-real system (green = +1 pt earned, red = 0 pts). Same color tokens as the match cards. The mechanic visually folds into the rest of the scoring system — no special treatment.
- **Empty/no-pick state:** if the user hasn't filled a third-place slot, show a muted placeholder (`Pick a 3rd-place team`) and the same `+1 pt` label. The cost of skipping is visible.
- **Disabled state (no third-place teams predicted yet):** if the user has filled fewer than 8 group-stage matches such that there aren't 12 distinct predicted third-place teams to pick from, dropdowns disable with a single line of explanatory text below the cluster: `Finish your group-stage predictions to unlock these picks.` One sentence, no banner, no warning chrome.
- **Don't:** badge the picks with trophy/star/lightning icons. Don't tint the dropdown background gold. Don't use a different border-radius from the rest of the form. The point is that this side-bet feels like part of the bracket, not a special mini-game.
- User then predicts R32 → R16 → QF → SF → Final + 3rd-place match by picking the winning *slot* for each match (`predicted_winning_slot_id` references a `bracket_slot`, not a `team`). Slot identity is stable; the team filling that slot is what changes as predictions and reality update.

**Reality phase (after a round actually plays):**
- Polling job ingests real results from api-football, writes to `matches.home_score` / `away_score` / `status`.
- Once group stage finishes, the polling job (or a manual update if the API is wrong) writes `bracket_slots.real_team_id` for the 32 R32 slots.
- User predictions are tied to slot IDs, not team IDs, so they survive the reality update intact.
- User can edit their predictions for the next round until that round's 4-hour-pre-deadline.

### Scoring

**Per match:**
- Match score correct: **3 points**
- Match outcome correct only: **1 point**
- Knockout-stage outcomes: must pick a winning team (no ties allowed in outcome predictions; score predictions can still be tied since penalties resolve them)
- **Knockout score-input UX:** when the user enters a tied score (e.g., 2-2) for a knockout match, a `Penalty winner` selector appears inline below the score inputs. Two pill-radios, one per team. The user MUST pick one before the prediction is considered complete. This is the visual reconciliation of premise 7 (canonical score = 90+ET) with the no-ties-in-knockouts rule.

**Tournament-wide bets:**
- Champion (Final winner): **5 points**
- 2nd place: **3 points**
- 3rd place: **1 point**

**Third-place R32 slot placements (the FIFA-literacy bet):**
- For each of the 8 R32 slots that take a third-place team, the user predicts which group's third-place team will land in that slot. **1 point per correctly-placed team.** Maximum 8 points across the 8 slots.
- "Correct" means: the team the user assigned to a given slot matches the team FIFA's actual third-place tiebreaker rule places in that same slot once group stage finishes. This bet rewards understanding FIFA's bracket structure (which group's 3rd-place CAN land in which R32 slot, given the eliminated-groups permutation).
- Scored once: when the polling job writes `bracket_slots.real_team_id` for the 32 R32 slots after group stage completes.
- A user who picks "3rd-place of Group F" for slot 5 scores 1 pt only if FIFA places Group F's 3rd-place team in slot 5. Picking a team whose group didn't qualify a 3rd-place team at all = 0 pts for that slot. No partial credit.

**Scoring totals (max possible):**

| Source | Matches/Items | Max points each | Subtotal |
|---|---|---|---|
| Group stage matches | 72 | 3 | 216 |
| Knockout matches | 32 | 3 | 96 |
| Finalist picks | 3 | 5/3/1 | 9 |
| Third-place slot placements | 8 | 1 | 8 |
| **Grand total** | | | **329** |

Scoring runs server-side when a match's status flips to `finished` via the polling job (or when third-place slots get populated post-group-stage), not live during play.

### Predicted vs. Real UX (the heart of the product)

Once a match finishes:
- Display predicted score next to real score, side by side.
- Color-coding:
  - **Green:** score correct (3 pts) — full prediction match
  - **Yellow:** outcome correct, score wrong (1 pt) — partial credit
  - **Red:** outcome wrong (0 pts)
- The user's locked-in prediction stays visible forever; reality renders alongside.
- The bracket diagram populates with actual teams as games complete, with the user's prediction shown as a smaller annotation on each match card.
- **Leaderboard refresh:** the leaderboard page polls every 30 seconds when open (simple `setInterval` + revalidate). Supabase Realtime is overkill for ~50 users and adds a moving part — defer it.

### Polling Job (GitHub Actions scheduled workflow)

- **Cadence:** hourly during match days. **Verified APT-3 (2026-05-09): Vercel Hobby cron is daily-only** (deployment fails on `0 * * * *` with `"Hobby accounts are limited to daily cron jobs"`). Pro plan ($20/month) is overkill for a 2-month hobby. Decision: **GitHub Actions scheduled workflow** (`.github/workflows/poll-results.yml`) hits a Next.js API route at `/api/cron/poll-results` hourly, with a shared secret in the `Authorization` header. Free tier covers 2000 min/month — hourly polling uses ~360 min/month, well under the cap.
- **Job:** fetch results for all World Cup matches from api-football. Upsert into `matches` (scores, status). Once group stage finishes, also write `real_team_id` onto the 32 R32 `bracket_slots`.
- **Note:** fixtures are NOT pulled from api-football — they're hand-curated and seeded before launch (premise 1). API is results-only.
- For any match whose status just flipped to `finished`: trigger scoring for all predictions on that match.
- **Idempotent scoring:** the scoring job MUST be safe to run twice. Vercel cron retries on transient failures, and a hand-trigger (e.g. via Supabase studio for late-arriving results) must not double-count points. Implementation: scoring writes `predictions.points_awarded` directly (set, not increment). Re-running scoring on an already-scored match yields the same value.
- **N+1 avoidance:** scoring loads the match + all its predictions in a single query, computes points in memory using `lib/bracket.ts` pure functions, and batch-updates predictions in one statement. Do not loop predictions and re-fetch the match each time.
- **Rate limits:** api-football free tier is 100 req/day AND 30 req/min on RapidAPI. Hourly poll = 24 req/day, well under both. Verify the per-minute limit holds during a peak match window when multiple matches finish simultaneously.
- **Failure mode:** if the API is unreachable, the job logs and exits cleanly. Manual edit via Supabase studio is the escape hatch.

### Performance Notes (5-50 user scale)

- **Leaderboard query is the hot path.** With every active user polling every 30s, the leaderboard endpoint runs frequently. Materialize total points: maintain `users.total_points` (or a `leaderboard` materialized view) updated only when scoring runs. Then the leaderboard endpoint is a simple `SELECT user_id, total_points FROM users ORDER BY total_points DESC` — cheap.
- **Bracket UI re-render cost.** A single mega-component holding all 72 group predictions + 31 knockout slots will be slow on older Android phones. Split into per-match components with local state; use `useMemo` for the cascade computation. Standard React performance hygiene.
- **30-second leaderboard polling is intentional**, but stop polling when the tab is hidden (`document.visibilityState === 'hidden'`). Saves Vercel function invocations and Supabase reads at no UX cost.

### Backups & Data Safety

- Enable Supabase's **Point-in-Time Recovery** (PITR) on the project, or set up a daily `pg_dump` to a private S3 bucket / GitHub-encrypted gist via GitHub Actions.
- Treat the `predictions` table as sacred — once locked, never DELETE, only soft-update. A bad migration mid-tournament that wipes predictions is the worst-case failure mode.

### Lock Enforcement Architecture

Source of truth: **Next.js API routes**. Every write to `predictions`, `predicted_third_place_assignments`, and `finalist_picks` goes through an API route that:

1. Authenticates the request (Supabase Auth session).
2. Loads the relevant `rounds.locked_at` (or finalist deadline = first match kickoff).
3. Compares to `now()` server-side. Rejects with 403 + clear error message if past lock.

Backup: **Supabase RLS policy** on `predictions` enforces the same check via the joined round. This catches any direct-from-client writes (e.g., a user using the Supabase JS client in their browser console). The API-route check is the user-facing source of error messages; RLS is the safety net.

Never trust the client. Never derive lock state from client time.

### Concurrent Edits

Multiple devices / browser tabs editing the same prediction: **last-write-wins**. No optimistic concurrency, no version columns. For ~50 family members the collision rate is effectively zero. If two writes race, the database accepts both and the later one survives. Acceptable.

### Cascade UI Reactivity (frontend)

When a user changes a group-stage score:
- The predicted standings recompute immediately.
- All R32 cards referencing `winner-group-X` / `runner-up-group-X` re-render with the new predicted team.
- All downstream knockout cards re-render with their cascade-derived predicted teams.

This must be wired so a single state change cascades visually in one render cycle. Use React Context or a Zustand store for predictions; derive standings and slots via `useMemo`. Don't try to manage cascade with refs or imperative DOM manipulation.

### Pure-Function Bracket Module

All bracket logic lives in `lib/bracket.ts` as **pure functions with zero database access**:

- `computeGroupStandings(predictions: Prediction[], groupTeams: Team[]): GroupStanding[]`
- `populateR32Slots(standings: GroupStanding[], thirdPlacePicks: ThirdPlacePick[]): SlotAssignment[]`
- `computeMatchPoints(prediction: Prediction, actualMatch: Match): number`
- `computeFinalistPoints(picks: FinalistPicks, finalStandings: FinalStandings): number`
- `computeThirdPlacePlacementPoints(predictedAssignments: PredictedThirdPlaceAssignment[], realR32Slots: BracketSlot[]): number` — for each of the 8 third-place R32 slots, awards 1 pt if the user's predicted team for that slot matches the team FIFA actually placed there. Scored once, after group stage finishes and R32 slots are populated.
- `computeLeaderboard(predictions: Prediction[], finalistPicks: FinalistPicks[], thirdPlaceAssignments: PredictedThirdPlaceAssignment[], users: User[]): LeaderboardEntry[]`

Pure means: same inputs → same outputs, no I/O, no Supabase. This makes them trivially unit-testable (Vitest, full coverage required — see Testing section). API routes and the polling job orchestrate Supabase reads and writes; they hand data to these pure functions and write the results back.

## Open Questions

1. **api-football results verification.** Manually inspect their World Cup 2026 *results* endpoint to confirm scores populate quickly and reliably after matches finish. **Action: do this in week 1.** If the API is slow or stale, plan B is a tiny `/admin` override page (Approach C) — accept the extra weekend.
2. **Leaderboard tiebreakers.** What happens if two users tie on total points? Suggested chain: most exact-score predictions → most outcome predictions → earliest registration timestamp. Confirm.
3. **Profile picture upload.** Supabase Storage works but is extra surface area. Recommended: use Google OAuth's avatar URL directly in v1, skip storage entirely.
4. **Deadline timezone.** "4 hours before first match" — store and display deadlines in UTC server-side; render in the user's local timezone client-side. The lock check must use UTC.
5. **Desktop-first** (revised in design review 2026-05-09). The bracket page is designed for a 1440px desktop layout: 60/40 split with prediction cards on the left and a sticky bracket tree diagram on the right. Mobile is a polish-pass concern, not a design-driver. Family members on phones get a single-column stack with the bracket tree behind a tab/modal. shadcn/ui handles the responsive collapse.
6. **Username moderation.** Public Google SSO + global leaderboard = profanity risk. Minimum: a small blocklist of obvious slurs in the username validator + a manual admin "rename user" path. Add a `users.is_banned` flag if it ever gets bad.
7. **Withdrawals / reschedules.** Unlikely but possible: a team withdraws, a match is rescheduled, a venue changes. Plan: rely on api-football to push the new schedule into `matches.scheduled_at`. If the source data is wrong, manual edit via Supabase studio. Worst case for predictions: any prediction on a withdrawn-team match resolves to 0 points (treat as not-finished).
8. **Account deletion.** A family member wants out. Implement a "delete my account" path that nukes `users` row + cascades; or just a soft-delete flag if cascade is risky mid-tournament.
